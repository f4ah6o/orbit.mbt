## 実装メモ

今回の実装対象は、前段で merge された `examples/wasm-webview/` の bridge を土台にした完了処理だった。bridge は `dispatch_event(kind, payload)` を単一入口にしており、browser 側の button click から `start_session`、`append_user_message`、`record_tool_request`、`record_tool_result` を呼ぶ。単一入口にすると、WebView とは「native app の中に埋め込む小さな browser 表示領域」という意味だが、その host 側は MoonBit の細かい API を知らなくても文字列の action だけ渡せばよい。

画面更新は `render_resource(project(session))` の HTML を `get_resource_html()` で取得して DOM に差し込む構成にした。DOM は Document Object Model の略で、browser が HTML を操作可能な木構造として持つ仕組みのこと。event log は JS 側で `dispatch_event` 呼び出しごとに追記し、AgentState の変化は HTML projection と snapshot JSON の両方で確認できる。

実際に wasm artifact を Node から instantiate してみると、最初は `_start` しか export されておらず、browser 側の `exports.boot()` が呼べないことが分かった。MoonBit の wasm link 設定では、公開関数を JS から呼ぶには `exports` に明示する必要がある。あわせて `use-js-builtin-string` を有効にした。これは MoonBit の `String` を host runtime の JavaScript `String` として渡せるようにする設定で、HTML や JSON を返す今回の bridge では必須になる。

`emit_html` を wasm import として MoonBit から JS に push する設計は issue に書かれていたが、現行 compiler では inline WAT import が assertion failure になるため、今回は README に制約を残したうえで JS が `get_resource_html()` を pull する最小構成を維持した。pull は host 側が必要なタイミングで値を取りに行く方式で、今回の demo では button action 後に必ず再描画するため十分に単純で安定している。
